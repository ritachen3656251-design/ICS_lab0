    -有过非正式的协同课程项目开发经历，当时我们没有使用git，而是采用了非常低效的方式，即一个同学把所有代码放在公开的github仓库（也邀请了我们作为仓库协作者），我们克隆代码后在本地机跑，最后通过压缩包再上传完整代码文件。我们一致认为，这种方式不仅无法让我们的工作实现并行，而且会大量修改函数和接口，导致返工，不是一种理想的合作方式。

    -为什么设计“暂存-提交”两个步骤：
    我的初步想法是，将代码放在暂存区有利于代码审查和修改，避免将带有bug或关键问题的代码直接提交，这一点在vibe coding时代也较为关键；而且可以在暂存区内选择性提交不同时期或不同功能的代码，便于特定版本的维护。在查阅相关资料后，我发现设计缓存区还有如下重要功能。
    一是便于把一次提交拆成多个逻辑，比如说如果一次文件改动中涉及bug、变量、注释等多处修复，可以分多次提交，保证每次提交逻辑干净、一目了然；
    二是便于处理突发情况。例如如果有某个功能的bug需要紧急修复，而当时开发者手上正在开发同文件的功能，可以先将需要修复的代码进行提交，保证同期工作不丢失。

    -根据git官方文档说明，git branch只会列出本地分支，当前分支前会标有 * 号；git branch -a会同时列出本地分支和远程追踪分支。
    所谓本地分支，是在本地仓库中创建和操作的分支，所有的提交都记录在这里；而远程跟踪分支是本地仓库中缓存的远程分支副本，命名格式通常为 origin/分支名，是本地对远程状态的快照，不能直接在这些分支上提交，git branch不会列出后者。

3. 在下面的三个网页中任选其二进行阅读，简要概括其内容，并谈谈你对“为什么要学习 Git”这个问题的理解。（15 分）

    - [Commit Message 规范](https://www.ruanyifeng.com/blog/2016/01/commit_message_change_log.html)
    - [Git Flow 分支控制](https://www.dafaycoding.com/article/git-gif-flow)
    - [语义化版本](https://semver.org/lang/zh-CN/)
    
    - Commit message概括：文章介绍了一种团队约定的提交说明格式，用 type 区分新功能、修复、重构等改动，用 scope 标明影响范围，用正文说明修改动机，并记录不兼容变更或关联问题。同时也介绍了辅助编写、校验提交信息以及生成更新日志的工具。
    - Git Flow概括：文章介绍了 Gitflow 的分支分工，master 保存发布版本，develop 汇集开发成果，feature 用于新功能，release 用于发布前验证，hotfix 用于紧急修复线上问题。同时给出了创建、合并分支和打标签的示例。
    原因：
    git 作为版本记录工具，可以让团队区分线上运行的是哪版代码，某次发布具体包含哪些改动。而且它使得项目或产品出现问题时，需要知道改了什么、何时改的、为什么改，git清晰的提交记录能减少排查，提高效率。
    git让多人开发可以协调，分支允许不同任务并行推进，合并把成果整合起来，配合代码评审和自动化测试，团队才能判断修改是否适合进入主线。
    同时git可以让线上问题可以控制，例如，新功能尚未完成时出现支付故障，可以从已发布版本建立修复分支，单独验证和发布，再把修复同步回后续开发，避免夹带未完成的功能。
