    -根据git官方文档说明，git branch只会列出本地分支，当前分支前会标有 * 号；git branch -a会同时列出本地分支和远程追踪分支。

4. 学习 Git 分支管理，新建 `feature` 分支，在该分支以及 `main` 分支上对 `main.c` 分别进行一次修改与提交（10 分）。随后将 `feature` 分支 merge 到 `main` 分支（即切换回 main 分支执行 `git merge feature`），并处理发生的合并冲突（10 分）。

    
    -本次实验中，我新建了 feature 分支，并在 feature 和 main 两个分支上分别修改 main.c 中的同一处代码，使其内容不同，然后各自完成一次提交。由于两个分支从共同版本出发，对同一位置进行了不同修改，合并时 Git 无法自动决定保留哪一方的内容，因此会产生冲突。
    -随后切换回 main 分支，执行 git merge feature。Git 提示 main.c 存在合并冲突，合并过程暂停。打开文件后，可以看到 <<<<<<< HEAD、=======和 >>>>>>> feature 等冲突标记，其中分别标出了当前 main 分支和待合并的 feature 分支的内容。
    -我根据预期功能整理冲突处的代码，删除冲突标记，保存最终版本，再执行 git add main.c 和 git commit，完成冲突解决及合并提交。最后通过git status 确认合并已经结束，并检查提交历史。
    实验报告中已经附上截图：一类展示执行 git merge feature 后的冲突提示及文件中的冲突标记；另一类展示解决冲突后的代码、合并提交结果和
  仓库状态。
    -通过本次实验，我理解了两个分支都修改同一个文件不一定会产生冲突；对共同版本中的同一行或重叠区域作出不同且无法自动合并的修改，才是
  本次实验触发冲突的关键。
    -对本次实验，出现冲突是由于两个分支对同一行做了不同修改，Git 无法自动决定采用哪个版本，因此会产生合并冲突，需要手动选择或整合内容。通常来说，当两个分支基于共同版本，分别对 main.c 的同一行或相互重叠的代码区域进行了不同修改，并各自提交后，合并时就可能出现冲突，因为 Git无法自动判断应该保留哪部分内容。此外，一个分支删除了另一个分支所修改的代码，或者一个分支删除了 main.c 而另一个分支修改了它，也可能导致冲突。如果两个分支修改的是互不重叠的区域，Git 通常可以自动合并。
